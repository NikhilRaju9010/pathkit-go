# Known limitations — PathKit for Go

PathKit maps what it supports and refuses, with a message, what it cannot map. Where it makes a quiet assumption instead, this page says so; read the lists below. This is the honest list of what it does and does not cover. How it works inside is in `docs/DESIGN.md`.

Go words used below: a *type assertion* is Go code that treats a value as another type; a *goroutine* (and a Temporal *coroutine*, `workflow.Go`) is a piece of code that runs alongside the rest; *single-assignment form* is the compiler's rewrite of the code in which every variable is written once; `-overlay` is a Go build flag that makes the build use other copies of some files (how `pathkit test` adds its recording code without touching yours).

## What is on the map

- **The package must compile.** PathKit uses Go's real type checker (`go/types` via `go/packages`), so a package with a compile error, or with modules not downloaded, cannot be analyzed. A Go toolchain (1.26 or newer) must be installed where PathKit runs.
- **One broken package stops the command.** If any package in `<folder>/...` does not compile, `analyze`, `coverage`, `report`, `pathkit test` and `pathkit traces` stop (exit 1) instead of skipping it, because skipping would silently shrink the set the coverage % is computed over. Every broken package is named on one line, with its first real error. A file position inside the current folder is shown relative to it; one outside is shown in full.
- **Workflows are recognized by signature.** A function or method counts as a workflow when its first parameter is `workflow.Context`, its last result is `error`, and it is exported. `RegisterWorkflow` calls are not looked at. An unexported workflow, or one that breaks one of these rules, can be listed in `.pathkitrc.json`'s `workflows.include` (its first parameter must still be `workflow.Context`); it is then labelled `added by config`. Dynamic workflows are not supported.
- **No following into other packages or child workflows.** A helper function in another package, or a child workflow started with `ExecuteChildWorkflow`, shows up as one step. What can go wrong *inside* it is not on this workflow's map. A child workflow mocked with `OnWorkflow` records nothing, because its code does not run; to cover a child workflow, test it directly.
- **Only code that runs in the workflow function itself is on the map.** Signal, query and update handlers registered with `SetQueryHandler`, `SetUpdateHandler` or a callback are separate entry points and are not followed.
- **Concurrency is not modelled.** Activities started together and waited on later, and coroutines started with `workflow.Go`, do not create junctions. A selector inside a `workflow.Go` coroutine or another closure is not mapped.
- **Activity, timer and signal calls are recognized only when made directly** through the Temporal `workflow` package's functions and types. A call made through your own wrapper function (`myExecute(ctx, ...)`) is not recognized as a Temporal call.
- **Only error checks right after a Temporal call, or after a helper that makes one, are junctions.** An `if err != nil` counts only when `err` last came from an activity, child workflow, timer, sleep, await or external-signal call in the same function (or, inside a selector callback, in that callback or the function around it), or from a call of a helper function of the same package that calls the Temporal SDK (see the next point). Other error checks are assumed to take the "no error" side. So a real run in which an error from a function that never touches the Temporal API takes the error return fits no path: add `//pathkit:branch` on that `if`. An `err` passed through several variables may not be traced back either; `//pathkit:branch` forces it.
- **Helper functions of the workflow's own package are followed, with limits.** The code of a helper that calls the Temporal SDK (or calls one that does) becomes part of the workflow's map, one copy per call, at most three helpers deep. This used to be a limit (the helper's errors were assumed to be "none", so a run in which a helper failed fit no path); that is fixed for these helpers. Still one step, as before: a helper in another package; a call through an interface or a function value (unless the variable is set once to a function literal); a call that is part of a bigger expression, in an `if` condition, or made with `go` or `defer`; a function that is itself a workflow (it has its own map); code that runs in `workflow.Go` coroutines or selector callbacks of a helper; a helper with no parameter named of type `workflow.Context`, with `goto`, Go `select`, a `workflow.Selector` or a type parameter; a method on a type with type parameters; a helper nested more than three deep; the second round of a recursion. (A workflow whose followed helpers give it more paths than the list holds is counted, staged and covered like any big workflow.) A helper's own error that is not the error of a modelled call (a wrapped error, a function value's error) is *unknown*: the check after the call is a junction labelled `name (helper)`, and both exits stay listed. A helper that never calls the Temporal SDK is ordinary code, however many decisions it has: they are not steps of the workflow, and an error check on its result is assumed to pass. Values the caller passes into a helper are not followed into it.
- **"Where did this `err` come from?" uses the nearest assignment above the `if`**, in the workflow function itself (including the `if`'s own `err := ...;`, but not inside closures). If `err` is set in different ways in different branches before the check, only the one written last counts. `//pathkit:branch` or `//pathkit:ignore` override the result.
- **An error check must compare the variable with `nil` and nothing else.** `if err != nil && retries > 3` is a plain `if` with `true`/`false` exits. When its true side returns `err`, the end is plain `End`, because the condition does not prove `err` is non-nil.
- **`//pathkit:ignore` on a plain `if` assumes the condition is false**, because an ignored `if` is usually a defensive check that does not fire; on an error check it assumes "no error". A pragma counts on the `if`'s own line or the line directly above (a comment trailing the previous statement counts too).
- **`&&` / `||` inside a condition is one junction**, with two exits, not one per part. Since version 0.5.0 each part is also recorded true or false when it is evaluated ("each part of a condition"; only for `if` and `for` conditions, and only in traces recorded by this version).
- **Some returns end at a plain `End`, with no kind.** PathKit names the end kind only when it is certain: `nil` is completed; `workflow.NewContinueAsNewError(...)` is continued-as-new; `fmt.Errorf`, `errors.New`, `temporal.New…Error`, or an error variable returned on the error side of its own nil check is failed. A bare `return` with named results, `return doSomething()`, or an error variable nobody checked prints plain `End`.
- **Junctions are treated as independent.** PathKit lists every combination of exits, even when the code makes some impossible. Example (`testdata/fixtures/switches`): `switch size` sets `lane`, then `if lane == ""` checks it, and PathKit lists `case "huge"` followed by `lane == ""` true, which cannot happen. Such paths show as missed unless classification marks them (detectors catch some shapes; rules and overrides the rest). Branch coverage is the fairer number for such workflows.
- **The path list stops at 2000 paths per workflow, but the count does not.** A workflow with more paths shows its exact number of paths, is cut into stages that are classified and covered one at a time, and has its impossible parts left out of the list (counted, with their proofs), so the 2000 listed paths are possible ones. Its path coverage is shown as incomplete: read its stage coverage and its branch coverage. A stage with more than `classification.stages.max_paths` paths (256) on its own is not listed; only its branch coverage is shown. The stage view uses the fact engine only (a rule, override or detector applies to whole paths, which only the first 2000 are); the parts of the map the list did not reach are counted, not classified. Facts across stages follow at most `classification.engine.max_contexts` (16) different incoming states: more than that, and an impossible answer is only needs-review, in that stage and in every stage after it until a stage is not followed. The settings can be raised (stage size up to 100000, states up to 1024), but the work grows with states times stage paths, so big values make a run slow. A test that ran a path beyond the list is counted and covers its stage paths; it is never unmatched. Splitting the workflow (for example into child workflows) makes every number exact again.

## Constructs

- **`goto` and Go's own `select` statement are never supported.** Such a workflow is skipped with a message that says why, for example `goto at x.go:12 is not supported: PathKit maps break, continue and return, but not goto`. (Temporal workflows use `workflow.Selector`, not Go's `select`.)
- **A `workflow.Selector` is mapped only in one safe shape.** Everything else is skipped with `workflow.Selector at <file>:<line> is not supported: <reason>`. The safe shape:
  - the selector is created once, with `workflow.NewSelector` or `NewNamedSelector`, in the workflow function;
  - its `AddReceive`/`AddFuture`/`AddSend`/`AddDefault` calls are plain statements in the same block, before the one `Select` call;
  - every callback is an inline `func` literal;
  - the selector variable is not passed to other code.

  A selector passed to a helper, an `Add…` inside an `if`, a loop or a closure, a named callback function, or two `Select` calls on one selector are refused: the exits could differ from run to run. `Select` itself may sit inside a loop.
- **A selector's exits are labelled by what they wait for**: `signal "<name>"`, `timeout` for a `NewTimer`, `activity <Name>`, `local activity <Name>`, `child <Name>`, and `default`. Anything PathKit cannot trace back to one of those calls (a channel made with `workflow.NewChannel`, a future passed in as a parameter) is labelled as written: `receive ch`, `future f`, `send ch`.
- **Wait results are recognized only as a plain `ok` or `!ok`.** `if !ok` after `ok, err := workflow.AwaitWithTimeout(...)` has exits `signaled` / `timeout`; after `ReceiveWithTimeout`, or with `c.ReceiveAsync(&v)` inside the `if`, `received` / `not received`. A compound condition like `if ok && x > 0` is an ordinary `true` / `false` junction.
- **A `switch` with only a `default` is not a junction.** `fallthrough` into the next case is not a separate step: the path shows the case the switch chose.
- **A `switch` with no `default` always gets a `default` exit, even when that cannot happen** (for example when the cases cover every constant of a small status type). That path then shows as missed. Workaround: write the `default` yourself (for example one that returns an error), or mark the path with classification.
- **Case labels are the source text.** `case StatusApproved` prints the constant's name, not its value; `case "a", "b"` stays one exit. Two cases with the same text get ` #2`, ` #3`.
- **The saga note says a compensation `defer` is registered, not that it ran.** A `defer` counts as compensation when the deferred call starts an activity, local activity or child workflow, directly or inside a deferred `func`. Every path that gets past it shows `[compensation (defer)]`, including the successful path. "Compensation ran" and "did not run" are not separate paths, because counting them would create impossible paths (a successful order that also compensated). A `defer cancel()`, a deferred log line, a deferred call to your own helper, and a `defer` inside a selector callback get no note. The note is in the text output, not in the `--mermaid` diagram.

## Newer shapes and what they cost (v0.3.0)

- **Summarized helpers give up precision, never correctness.** When a workflow is over the path cap and calls helper functions, each helper is mapped once and a call is one step (`classification.helpers.mode`). A claim that a path is impossible inside such a helper is made without knowing what the caller passed in, so fewer paths are shown as impossible there; the caller's own claims use no knowledge of what the helper did to a value it was handed (a pointer, a map), as for any call PathKit does not follow. A helper that is summarized is covered when any call takes a branch: the report cannot say which call did.
- **Summarize is for a whole workflow, not per helper.** In `auto` mode a workflow either has every helper copied in or every helper summarized.
- **Old traces of a workflow that changed to summarized helpers are converted only while the workflow's code is unchanged since they were recorded.** After a code change they are stale like any other trace.
- **Helpers deeper than three levels, a helper that calls itself, and a helper whose code holds `goto`, `select`, a `workflow.Selector` or a type parameter are not mapped**; they are listed in the "could not fully read" panel with the reason.
- **A function that returns the error of a Temporal call directly (`return fut.Get(...)`, `Sleep`, `Await`) is one path by default.** A test of the failure and a test of the success both cover it. `classification.direct_returns: "step"` makes it two paths, but it changes the stable ids of the paths through it, and only in the workflow function itself, not in a helper. `AwaitWithTimeout` returns two values and is not one of these shapes.
- **A closure that calls the Temporal SDK is not mapped unless it is a selector callback, a handler or a deferred compensation.** A goroutine started with `workflow.Go` is listed as "closure not mapped": its calls are not steps of any path.
- **A future nobody reads is not a step**, and its failure is not a decision. The panel lists it. A future kept in a variable that is used only to be passed on (to a function, a slice, a selector) counts as read.
- **Update handlers and validators are mapped only when they are a function literal in the registration or a function or method of the workflow's own package.** A handler held in a variable or defined in another package is listed in the handler table with the reason. A validator that rejects by panicking is listed too: a path that panics is not a path.
- **A query handler has no map of its own** (it takes no `workflow.Context`, so a run cannot be recorded in it), and whether a test sent a query cannot be seen: the handler table says `not recorded`. The same holds for a signal read with a plain `Receive` (no decision shows it), and for any handler when every trace of its workflow comes from a recorder before v0.3.0.
- **The kinds of failure of a call (timeout, cancelled, application error, non-retryable) are not paths.** The code's own `if` on the error is the decision; the call outcome table lists the kinds the code branches on and whether a test took them. A kind the code does not branch on is not listed.
- **Loop rounds are read from the recorded runs; the path model stays one round per loop.** Whether 2 or more rounds can happen is not worked out (only "a loop that must run at least once" and "a loop with no exit of its own" cannot run 0 rounds). `classification.loops.model: "zero-one-many"` is reserved; PathKit warns and keeps the one-round model.
- **A stage that is cut into pieces is judged piece by piece with nothing known on the way in.** This is sound (a claim never needs more than the piece's own decisions) but finds fewer impossible paths than the stage-to-stage chain does. A stretch with no nested region to cut at keeps the old behaviour: it is not listed and has branch coverage only.
- **The CI floor leaves out a stage that is too big to list and could not be cut.** For a workflow over the cap, `fail_under_testable` counts the stage paths of the stages that are listed; a stage not listed is not in the number (its branch coverage is in the report). Use `ci.capped_basis: "branch"` to count the branches of the whole map instead.
- **Several modules in one folder are read only when the folder is not inside a module** (or holds a `go.work`). A separate module inside the module you run PathKit in is not read; run PathKit in its folder.
- **`classification.activity_wrappers` takes a function by name, and trusts you.** PathKit does not check that the function really starts an activity; it treats a call as a step with the outcomes success and failure when its error is checked.

## Loops

- **Loops follow the loop rule.** A loop is a junction when it contains a Temporal call or any junction. It adds at most three kinds of path: not entered, entered and left from inside, and entered, went round, then left. A run that goes round many times is folded onto one of those by keeping only its last trip, so "failed on the 1st trip" and "failed on the 5th trip" are the same path, and the number of trips is never shown.
- **Any call into the Temporal SDK makes a loop a junction**, even one that does not wait, such as `workflow.GetLogger(ctx).Info(...)`.
- **A loop with no Temporal call and no junction is walked once.** PathKit assumes it runs its body once and records nothing for it. If such a loop's body can `return`, the paths where the loop is not entered are not listed; a `for {}` of this kind with no `break` has no normal way out, so its paths are not listed at all. PathKit warns about a workflow that ends up with no paths (in the text report and on stderr) and does not count it in the totals. A `for {}` loop that contains a Temporal call (a `workflow.Sleep`, say) but no `break` or `return` has no way out either, so it gets the same warning.
- **A `for {}` loop has no "not entered" path**: it always goes in, and leaves only by `break` or `return`.

## Recording (`pathkit test`)

- **Coverage is recorded only by `pathkit test`, not by plain `go test`.** A plain `go test` compiles your original workflow files, so it records nothing while your tests still pass or fail as usual. `coverage` and `report` then say `no trace files found in <dir>; coverage is recorded only by "pathkit test" (plain "go test" records nothing)`. `pathkit prepare` prints the `-overlay` command for running `go test` yourself; it copies the code as it is at that moment, so after a change run `prepare` again (otherwise the traces are stale, and reported as such).
- **A skipped test records nothing, and PathKit does not tell you which tests were skipped.** The paths it would have run show as missed. Run `pathkit test ./... -- -v` to see the `SKIP` lines. A test that fails still records the paths its workflows took.
- **`pathkit test` always runs tests fresh.** It adds `-count=1` (unless you pass your own `-count`), because Go's cached test results would skip the tests and record nothing.
- **A trace does not say which test produced it.** The workflow runs on its own goroutine and cannot see the `TestXxx` that started it. To connect one test to its path, run just that test: `pathkit test <folder> -- -run '^TestName$'`.
- **A run counts only if it finished a `return` of the workflow function.** A run that panics (even while computing its return value), times out, or is stopped by the SDK is saved as `incomplete` and never matched. Trace files are written when the workflow function exits, so a run left blocked forever produces no trace.
- **The staleness hash ignores comments and formatting, but nothing else.** Renaming a variable inside the workflow function marks its old traces `stale`. Editing a different function, or another file, does not. The hash uses only the function's Go tokens, so it is the same on Linux, macOS and Windows.
- **Some names are reserved in recorded packages:** `pathkitRec`, `pathkitStart`, `pathkitRecorder`, `pathkitTrace`, `pathkitTraceDir`, `pathkitLoop`, `pathkitCtx` and `pathkitRet1`…`pathkitRet8`. If your package already uses one, recording stops with a clear error.
- **A workflow function with more than 8 results, or whose parameters have no names at all** (`func W(workflow.Context, int)`), cannot be recorded; `pathkit test` stops with a clear error. A context parameter written `_` is fine.
- **In a recorded `range` loop, PathKit adds a call after the loop's closing `}` and before each `break` that leaves it**, on the same lines, so line numbers do not change.
- **`pathkit test` writes its marked-up copies to `.pathkit/overlay/`** in the folder you run it from, and deletes only its own files there. Go's build and test commands never look there, but `gofmt -l .` does; add `.pathkit/` to your `.gitignore` and run gofmt on your tracked files.
- **Two workflows with the same package name and function name in different folders** are named with the shortest unique tail of their import path (`a/dup.Work`, `b/dup.Work`). With a `.pathkitrc.json` the names are decided over the config's packages; without one, over what the command loaded, so record and report on the same folder (`./...`). Trace files record the workflow's package; a trace that names another package is "unknown workflow", never counted.

- **Run `go test -overlay=...` from the real folder, not through a symbolic link.** A symbolic link is a folder name that points at another folder (macOS temporary folders are one: `/var` points at `/private/var`). `pathkit test` handles this itself. The command that `pathkit prepare` prints is run by your own shell, whose working folder keeps the link's name, and then the Go tool does not match the copied files and records no traces (`recorded 0 traces`). `cd` into the real folder (`cd -P .` does it) before running it.

## Coverage and reports

- **Branch coverage uses raw steps**, before loop folding, so a branch can show as taken even when no covered path uses it. It is shown only; `--fail-under` uses path coverage.
- **Traces that do not count never change the exit code.** A stale, unmatched, incomplete or unreadable trace is a warning on stderr and a number on the `Traces:` line. A CI job that must fail on those should check the `traces` counts in `--json`.
- **`--allow-stale` trusts that the change was cosmetic.** A stale trace that still fits a path is counted (marked `(stale trace)`), even if the change altered what that path does.
- **`coverage --clean` and `report --clean` delete traces only after a full report** (exit 0 or 2), never after an error.
- **Priority labels are per workflow, not per path.** High (below 50%), Medium (50–80%, both included) or Low (above 80%), compared exactly with whole numbers. A workflow with no paths gets no label.
- **Colour appears only on a real terminal**, never when the output is piped or redirected, with `--no-color`, config `noColor`, or `NO_COLOR`. The `--out` file and `--json` never have colour.
- **`report` takes folders, not single files.** With no folder it uses every entry of the config's `packages`; a workflow reached through two entries is counted once.
- **The HTML page is a snapshot of one run**, has no diagram (use `analyze --mermaid`), needs JavaScript for its path tables (the summary and the glossary work without it), and needs `=` to name a file (`--html=out.html`). Its trend covers the last 5 `report --html` runs written to that folder; a CI job starting from a fresh checkout starts the trend empty unless it keeps `report-history.json`.
- **`--version` shows a commit-based version for local builds**, for example `v0.0.0-20250101000000-abcdef123456+dirty`; `go run` prints `dev`. Only release builds and `go install ...@vX.Y.Z` show a clean `vX.Y.Z`.

## Scope (`.pathkitrc.json`)

- **`include` means "only these count".** Every other workflow is listed as excluded with the reason `not in include list`, never dropped silently.
- **An in-scope workflow PathKit cannot analyze is always printed, and blocks `coverage` and `report` with exit 1.** Fix it, or exclude it with a reason.
- **Names are checked against the whole configured `packages`**, so a misspelled name is caught even when you analyze one file; PathKit then loads those packages once more.
- **`pathkit test` and `pathkit traces` without a folder use the config's `packages` only when it lists exactly one.**
- **The config search stops at the folder with `go.mod`.** Use `--config <file>` to name a file anywhere. On Windows, a config path such as `/abs/x` (no drive letter) is relative to the config file; write `C:/abs/x`.

## Path classification

- **`stableId` changes when a condition's text changes.** It is built from the printed text of each decision, so renaming a variable in an `if` changes the `stableId` of every path through it, and a saved override or acceptance then shows as stale (a warning; the path is testable again). It does not change when an unrelated junction is added or removed. `pathkit explain` and `report --json` show the current ids.
- **A rule's entries are copied from `pathkit analyze`** and matched as exact text (spaces collapsed). A `when` entry that matches nothing makes the rule stale (a warning); a `without` entry that matches nothing is an error. A rule can only list decisions: it cannot say "this loop ran at least twice" or compare values.
- **Identical decision text must be numbered.** In a workflow with several decisions of the same text, write `if more #2 --false` (`#1` is the first) or `any: if more --false`. `#n` counts in source order, so a decision added above shifts it: `#2/3` turns the rule off with a warning when the count changes, and with a CI baseline every numbered entry warns when its decision changed place on the map. Without a baseline, a bare `#2` has no such protection. The place check can also warn when `#2` is still right, and cannot see two identical decisions whose bodies (with no decision inside) are swapped.
- **A `//pathkit:untestable` comment marks one exit of one decision**, on the decision's own line or the line above; a combination needs a rule. It is checked even when classification is off: one that cannot be used makes the workflow "not analyzable", never silently ignored.
- **Names in the classification section are checked against every top-level function**, so an override naming an unexported helper resolves and is then reported stale. Entries for excluded or unpicked workflows are neither applied nor checked.
- **The classification block is off unless asked for** (`--coverage-basis`, or `"classification": {"enabled": true}`). Off, `--fail-under` checks overall coverage exactly as without classification. The JSON has the classification fields all the time.
- **A trace that fits no path** makes that workflow's detector and rule claims needs-review until the trace is fixed, re-recorded or accepted in `classification.explained_traces` with a reason. Its steps id uses junction numbers, so it changes when the decisions are renumbered. A trace that fits a path beyond the list is not unmatched, so it is never unexplained.
- **The CI baseline compares stable ids.** Editing a condition's text makes its paths look new, and a lost test is caught only while its path's stable id is unchanged. Only the listed paths are in the baseline; `classification.ci.stage_floor` checks stage coverage instead for big workflows.
- **`scripts/project-baseline.sh` builds a copy of the project.** A `replace ../sibling` in `go.mod` or a `go.work` pointing outside the project will not build in the copy.

## Automatic detectors

- **Not detected yet** (a person can still use the label with a mark or a rule): `dead-code` and `after-continue-as-new` (code after a `return` has no path), `update-handler-continue-as-new`, `rejected-update-invisible` and `unfinished-handlers` (handlers are not followed), `concurrency-order` (a person may set it), `workflow-task-failure` (paths into `panic` are dropped), `side-effect-error` (an error check after `SideEffect` is a junction only with `//pathkit:branch`), and `either-or-wait`. `model-limit` is set only by PathKit itself, on a claim it does not trust. `loop-minimum`, `set-then-test` and `depends-on-missing` are config rules only.
- **`closed-signal-channel` is an assessment, not a proof.** The Temporal SDK and server do not close signal channels, but code can turn another handle of the same named channel into a `workflow.Channel` with a type assertion and close it. So when the package has a type assertion on a channel interface, or passes a channel to another package, the claim is not made for the affected names and the path goes to needs-review. A channel declared with `var` and assigned later is "origin unknown" (needs-review).
- **What the automatic detectors assume about Temporal and your project.** These are things PathKit does not check, so a project that breaks one of them can have a path marked cannot-be-tested that a test could reach:
  - *SDK version:* "the SDK does not close signal channels" was checked in the source of one SDK version (v1.49.0, named in the `closed-signal-channel` definition). A much newer or older SDK was not read.
  - *No custom interceptors:* an interceptor is your own code, registered on the worker or on the test environment, that sits between the SDK and the workflow and can replace what a workflow call such as `workflow.GetSignalChannel` returns. One could hand the workflow a channel it has already closed. PathKit does not look for interceptors. If you use them, check the `closed-signal-channel` claims, or turn that detector off with a reason.
  - *Results are not changed after `Get`:* `contradictory-get-result` and `contradictory` assume that the value an activity result is decoded into is changed only by the workflow code PathKit reads. A test cannot change it afterwards: the result is decoded into a fresh value. A mock returns one result per call, and a retry happens before `Get` returns.
- **`contradictory`, `contradictory-get-result` and `same-list-loops` only claim what they can prove.** They use the compiler's single-assignment form and strict shape checks, so they miss many real cases and never guess. Not claimed: a decision inside a loop, a selector callback or a function literal; a value read through a pointer, from a map, from a channel or from a call; a list that is re-sliced, appended to or re-assigned; a `Get` in a loop, closure, `defer` or `go`.
- **`list-built-from-list` and `loop-exit-before-first-trip` claim only their exact shapes**: one plain append per trip into a list that starts empty and nothing else touches; a `for cond` loop on a local plain `bool` set to a constant. A flag set only by other conditions and tested later (a set-then-test shape) is not detected; use a rule.
- **`constant-condition` reads only `if` conditions** and never follows a constant from another package.
- **The fact engine (`value-flow`, `possible-correlation`) claims only what it can follow, and forgets the rest.** It follows plain local values (strings, numbers, bools, nil-ness of pointers, maps, slices, interfaces) and fields of structs held by value. It never follows: package-level variables, map or slice elements, a field behind a pointer, a value whose address is taken (`&x`, `Get(ctx, &x)`, `Receive(ctx, &x)`) or that a pointer-receiver method is called on, a value a closure writes (`workflow.Go`, a selector callback, `defer`), a value a loop assigns (after the loop starts), a value an `if` or loop that PathKit does not decide assigns, or the result of a call. A function with `goto`, `recover` or the `unsafe` package is left alone. So it misses real cases; the leftovers show as testable (or as `possible-correlation` for an untested path that asks about the same value twice). It follows the types an interface value can hold only for values built in the function and for values Temporal decodes (see the next two points); a type switch on any other interface value is not claimed (`unknown-input-type` asks a person for untested paths). Facts do not cross activities: two activity results that are related are unknown to it.
- **Slices and maps are followed only while nothing else can reach them.** A slice or map that is passed to any call (activity arguments too), copied, deleted from, sliced, captured by a closure, written through an alias or has its address taken is not followed at all, even if the call does nothing to it. Element writes through an index, `append(s, x)` back to the same variable and a range over it are followed. A map lookup of a key PathKit cannot prove is in the map may give nil. Slices and maps nested in other values are not followed, except the containers found inside a decoded value (see the next point). A slice literal with indexes, a map with interface keys, and a value the workflow takes out of an interface and hands to other code are not followed.
- **Assumption `no-custom-interceptor`.** A slice or map handed to `workflow.ExecuteActivity`, `ExecuteChildWorkflow` or `SignalExternalWorkflow` keeps what PathKit knows about it, because the SDK encodes those arguments when the call is made and the callee works on a copy; claims that rely on this say so. `ExecuteLocalActivity` is not one of them (it passes the map itself and may change it), nor is any other call. PathKit turns this off by itself when it finds code that registers a custom interceptor anywhere in the module (an `Interceptors` option, a type built on the SDK's interceptor base types, or an `InterceptWorkflow` method; comments and strings do not count), and says so in every report; an interceptor set up where PathKit does not read (another module) is not seen, so turn it off yourself with `classification.assumptions.no_custom_interceptor = "off"`. A struct that holds the map and was put in a variable before the call is not covered.
- **Assumption `default-json-converter`.** Claims about values Temporal decodes (`impossible-type`) assume the default JSON converter: an `interface{}` holds only a string, float64, bool, nil, `[]interface{}` or `map[string]interface{}`. PathKit turns this off by itself when it finds code that sets a custom data converter or payload codec anywhere in the module (a client or worker option named `DataConverter`, `NewCodecDataConverter` / `NewCompositeDataConverter`, or a type with a converter's methods; a syntax search of every Go file of the module, folders named vendor, testdata, node_modules, .git and .pathkit excepted; a comment or a string does not count, and a symbolic link to a folder is not followed), and says so in every report. `UseNumber` and `json.Number` do not switch it off; they change only the decoder that uses them. A value your workflow decodes itself with `json.Unmarshal` or a `json.NewDecoder` decoder without `UseNumber` follows from the standard library and needs no assumption. Only the futures and channels that carry payloads are treated as decoded (an activity, local activity, child workflow or external signal future, a signal channel, SideEffect and MutableSideEffect); a channel or future the workflow makes itself (NewChannel, NewFuture) hands over Go values untouched and is not. A converter set somewhere PathKit does not read (a module that is not one of the workflows' modules, a replaced dependency) is not seen: turn it off yourself with `classification.assumptions.default_json_converter = "off"`.
- **A branch that is dead only because of a bug is also called impossible by the fact engine** (`constant-condition` or `value-flow`), because the code really cannot reach it. PathKit cannot tell a bug from a design; read the proof (`pathkit explain`) and fix the code if it is a bug. Until it is fixed, a rule or `mark_untestable` entry with the label `known-defect` moves the path to needs-review and counts it under "Blocked by known bugs".
- **History limits and version gates can be tested.** The SDK's test environment has `SetContinueAsNewSuggested`, `SetCurrentHistoryLength`, `SetCurrentHistorySize` and `OnGetVersion`, so those paths are `needs-special-test`, not cannot-be-tested.
- **The classification block still counts the listed paths of a big workflow.** Only the three headline numbers leave them out; "Testable coverage: N / M" in the classification block, the per-bucket counts and the old JSON keys (`total`, `branches`, `classification`) are over listed paths.
- **Missed-path groups, `rules check` and `suggest` look at listed paths only.** For a workflow with more paths than the list holds, a group, a hit count or a draft covers the listed paths; an entry that hits none of them is not called stale. A group that is a stage path of a big workflow is not shown.
- **`known-defect` is a person's word.** PathKit cannot check that a bug exists; the entry stays until you remove it, and `rules check` only tells you when it hits nothing or a test ran the path.
- **The assumptions panel counts claims, not paths, for left-out parts of the map**: a pruned group is one claim however many paths it holds, and stage-only claims on paths beyond the list are not counted.

## Scenarios, the main number and the advice

- **A scenario is what PathKit can see from outside.** It knows the calls it reads (see "Scenarios, the main number and the project headline" in SETUP-GUIDE.md). A place it could not read (the "could not fully read" panel) gives the path a scenario of its own; a workflow over the path cap with such a place has its scenarios `not measured`. A helper call that is summarized counts as known only when its arguments are constants or unchanged parameters.
- **Over the cap, scenarios are counted from the shape of the map, not from checked paths.** The count can include scenarios that cannot happen (the fact engine proves impossibility path by path), and scenarios no listed path makes are counted as testable. The number is pessimistic, never optimistic.
- **Two runs of one path can differ inside a summarized helper.** The scenario says "the helper was called", not what happened inside it.
- **The scenario check cannot tell an extra step next to a loop from an earlier round of that loop.** A loop is read once per path, so its earlier rounds may make other calls; a run's list of calls has no marks for rounds, so one extra call placed directly before or after the loop looks like such a round and is not reported (an extra call anywhere else is).
- **The scenario's failure kind is only what the code branches on.** A workflow that ends with `return err` has the end `failed`, not the kind of error.
- **Cleanup after a cancel is not its own stage.** `cancel()` (from `workflow.WithCancel`) is a step of the scenario, but the code that runs after a cancel is not cut into a stage of its own. Since version 0.5.0 the decisions that run under a context from `workflow.NewDisconnectedContext` (checking a call made with it, or written after it in the same block) are marked, and the page's checklist shows them as a labelled block "Cleanup after a cancel"; cleanup written in a deferred function literal is a closure and is not mapped.
- **Test names are best effort.** The recorder finds the test by looking at the goroutine that waits in the Temporal test environment's `ExecuteWorkflow`; with parallel tests (`t.Parallel()`) it cannot tell which is its own and leaves the name blank. A subtest is named by its top-level test.
- **Scaffolds need a function to mock.** An activity that is a method value, or is started by a text name, gets a `// TODO:` instead of a mock; a signal gets a `nil` payload unless a later decision reads a field of what the signal carries (then the scaffold builds it); a decision on a value PathKit cannot trace to the input, an activity's result or a signal's payload (a method call, a local variable, an update's payload) is left as a TODO line that names the condition. A scaffold covers the scenario only if its TODO lines are right.
- **Item ids are scenario ids** and two workflows that make the same steps have the same id; `pathkit scaffold --workflow` picks one.
- **`pathkit diff` compares what PathKit can read** at both refs; it needs a git repository and a checkout that builds at the base. Decisions are matched by their text, so a rewritten condition is one removed and one new decision.
- **`--no-network` is Linux only** and needs `unshare` with unprivileged user namespaces; elsewhere it refuses.


## Branch coverage, the decision check and the engine (version 0.5.0)

- **A workflow over the path cap removes no outcome as "can't happen".** Proving an outcome impossible needs every path through it, and a workflow whose list is not whole does not have them; branch coverage then counts every outcome PathKit can see, so it can look lower than the truth, never higher.
- **A helper's outcome is one outcome, covered when any call covers it.** A helper called from two places can have one place never tested and still show as covered; the per-call-site detail is in the JSON (`sites`, `sitesTaken`).
- **"Each part of a condition" needs traces from this version** and counts only `if` and `for` conditions that are chains of `&&` and `||`. Parts after the one that decides are not evaluated, so some values are never seen on purpose (the count says "seen", not "possible").
- **The decision check forces only a plain `if` and the `err != nil` check of an activity, child workflow or timer.** Switches, loops, waits on several things and `return call()` checks are listed as not checked. Forcing "failure" gives the code a plain non-retryable application error: a decision that branches on another kind (a timeout) is not forced into that kind. The score is only as good as the tests that went through the decision (found from the test names in the traces; a parallel test has no name, so the package's tests run).
- **"No visible effect" is the scenario model's judgment**, not a proof: it says the scenarios through the forced outcome are those of the other outcomes. It is only used for a decision no test noticed, to tell it apart from one a test should have checked.
- **Summaries of plain functions are conservative.** A function of the same module is summarized only when it is simple (see docs/DESIGN.md D32): a function with named results, `defer`, a map it hands on, a call through an interface or a function value, a file with a build condition, or more than three calls deep is unknown, and an unknown result makes paths look possible, never impossible. Only packages PathKit was asked to read in the same run can be summarized (`./...` reads them all).
- **A map built step by step inside the workflow is followed only until it is handed on.** While the workflow function alone has touched it, PathKit knows the type each key holds. Once the map is passed to a call, stored in a request or otherwise handed on, the callee could change it, so a later type check on its values keeps all cases possible: those paths stay testable. A map built by a plain function of the same module is read key by key in the same way until it is handed on.
- **A map or slice held in a field of a struct is not followed.** Every copy of the struct shares that map or slice, and PathKit does not follow where a struct goes, so it keeps no fact about its length, elements or keys; a check on them keeps both sides possible. The same holds for a map or slice from the moment it is handed to a call: what was known before the call is not used after it.
- **A "possible bug" (`likely-defect`) is found for a type switch case and a comparison of an interface with a constant**, not for a type assertion `x.(T)` yet. After one on a path, PathKit makes no further "can't happen" claim on that path, because its notebook then holds a premise the code contradicts.
- **`&x` is forgotten at the call that writes through it** only for the calls PathKit knows (the `Get` and `Receive` methods of the Temporal SDK, `json.Unmarshal`, a decoder's `Decode`); any other use of `&x` still stops PathKit from following the variable in the whole function.
- **Scaffolds fill values for decisions that read the input, an activity's result or a signal's payload**; conditions it cannot turn into values (a method call, an ordering of texts, a value it cannot trace) stay TODO lines, and a scaffold reaches its scenario only when those lines are right. On the sample fixtures 7 of 9 scaffolds reach their scenario with no edit.
- **`pathkit next` ranks by the least risky untested path through an outcome.** The risk word names the riskiest thing a test of the outcome must do, not the risk of the code.
- **A selector built and used in one chained expression is mapped** (`workflow.NewSelector(ctx).AddFuture(...).Select(ctx)`); a selector with two `Select` calls and one with `AddFuture` in a loop are still reported.
