# Known limitations — PathKit for Go

PathKit maps what it supports and refuses, with a message, what it cannot map. Where it makes a quiet assumption instead, this page says so; read the lists below. This is the honest list of what it does and does not cover. How it works inside is in `docs/DESIGN.md`.

Go words used below: a *type assertion* is Go code that treats a value as another type; a *goroutine* (and a Temporal *coroutine*, `workflow.Go`) is a piece of code that runs alongside the rest; *single-assignment form* is the compiler's rewrite of the code in which every variable is written once; `-overlay` is a Go build flag that makes the build use other copies of some files (how `pathkit test` adds its recording code without touching yours).

## What is on the map

- **The package must compile.** PathKit uses Go's real type checker (`go/types` via `go/packages`), so a package with a compile error, or with modules not downloaded, cannot be analyzed. A Go toolchain (1.26 or newer) must be installed where PathKit runs.
- **One broken package stops the command.** If any package in `<folder>/...` does not compile, `analyze`, `coverage`, `report`, `pathkit test` and `pathkit traces` stop (exit 1) instead of skipping it, because skipping would silently shrink the set the coverage % is computed over. Every broken package is named on one line, with its first real error. A file position inside the current folder is shown relative to it; one outside is shown in full.
- **Workflows are recognized by signature.** A function or method counts as a workflow when its first parameter is `workflow.Context`, its last result is `error`, and it is exported. `RegisterWorkflow` calls are not looked at. An unexported workflow, or one that breaks one of these rules, can be listed in `.pathkitrc.json`'s `workflows.include` (its first parameter must still be `workflow.Context`); it is then labelled `added by config`. Dynamic workflows are not supported.
- **No following into other packages or child workflows.** A helper function in another package, or a child workflow started with `ExecuteChildWorkflow`, shows up as one step. What can go wrong *inside* it is not on this workflow's map. A child workflow mocked with `OnWorkflow` records nothing, because its code does not run; to cover a child workflow, test it directly.
- **Only code that runs in the workflow function itself is on the map.** Signal, query and update handlers registered with `SetQueryHandler`, `SetUpdateHandler` or a callback are separate entry points and are not followed.
- **Concurrency is not modelled.** Activities started together and waited on later, and coroutines started with `workflow.Go`, do not create junctions. A selector inside a `workflow.Go` coroutine or another closure is not mapped.
- **Activity, timer and signal calls are recognized only when made directly** through the Temporal `workflow` package's functions and types. A call made through your own wrapper function (`myExecute(ctx, ...)`) is not recognized as a Temporal call.
- **Only error checks right after a Temporal call are junctions.** An `if err != nil` counts only when `err` last came from an activity, child workflow, timer, sleep, await or external-signal call in the same function (or, inside a selector callback, in that callback or the function around it). Other error checks are assumed to take the "no error" side. So a real run in which an error from your own helper function takes the error return fits no path: add `//pathkit:branch` on that `if`. An `err` passed through several variables may not be traced back either; `//pathkit:branch` forces it.
- **"Where did this `err` come from?" uses the nearest assignment above the `if`**, in the workflow function itself (including the `if`'s own `err := ...;`, but not inside closures). If `err` is set in different ways in different branches before the check, only the one written last counts. `//pathkit:branch` or `//pathkit:ignore` override the result.
- **An error check must compare the variable with `nil` and nothing else.** `if err != nil && retries > 3` is a plain `if` with `true`/`false` exits. When its true side returns `err`, the end is plain `End`, because the condition does not prove `err` is non-nil.
- **`//pathkit:ignore` on a plain `if` assumes the condition is false**, because an ignored `if` is usually a defensive check that does not fire; on an error check it assumes "no error". A pragma counts on the `if`'s own line or the line directly above (a comment trailing the previous statement counts too).
- **`&&` / `||` inside a condition is one junction**, with two exits, not one per part.
- **Some returns end at a plain `End`, with no kind.** PathKit names the end kind only when it is certain: `nil` is completed; `workflow.NewContinueAsNewError(...)` is continued-as-new; `fmt.Errorf`, `errors.New`, `temporal.New…Error`, or an error variable returned on the error side of its own nil check is failed. A bare `return` with named results, `return doSomething()`, or an error variable nobody checked prints plain `End`.
- **Junctions are treated as independent.** PathKit lists every combination of exits, even when the code makes some impossible. Example (`testdata/fixtures/switches`): `switch size` sets `lane`, then `if lane == ""` checks it, and PathKit lists `case "huge"` followed by `lane == ""` true, which cannot happen. Such paths show as missed unless classification marks them (detectors catch some shapes; rules and overrides the rest). Branch coverage is the fairer number for such workflows.
- **Path enumeration stops at 2000 paths per workflow.** A workflow that reaches the cap gets a loud `WARNING` at the top of the text report, a banner in the HTML page and a `pathCapWarning` field in the JSON, and its line says `truncated at maxPaths=2000`. Its path list, classification and coverage are then incomplete: paths beyond the cap are not listed, not classified and not counted, so read its numbers as a lower bound. Branch coverage keeps giving a useful number beyond that. A run that took a path beyond the first 2000 is a warning, not counted, and a config entry that matches none of the listed paths is reported as "beyond the path cap", never as stale. The fix is to split the workflow (for example into child workflows) so each stays under the cap.

## Constructs

- **`goto` and Go's own `select` statement are never supported.** Such a workflow is skipped with a message that says why, for example `goto at x.go:12 is not supported: PathKit maps break, continue and return, but not goto`. (Temporal workflows use `workflow.Selector`, not Go's `select`.)
- **A `workflow.Selector` is mapped only in one safe shape.** Everything else is skipped with `workflow.Selector at <file>:<line> is not supported: <reason>`. The safe shape:
  - the selector is created once, with `workflow.NewSelector` or `NewNamedSelector`, in the workflow function;
  - its `AddReceive`/`AddFuture`/`AddSend`/`AddDefault` calls are plain statements in the same block, before the one `Select` call;
  - every callback is an inline `func` literal;
  - the selector variable is not passed to other code.

  A selector passed to a helper, an `Add…` inside an `if`, a loop or a closure, a named callback function, or two `Select` calls on one selector are refused: the exits could differ from run to run. `Select` itself may sit inside a loop.
- **A selector's exits are labelled by what they wait for**: `signal "<name>"`, `timeout` for a `NewTimer`, `activity <Name>`, `local activity <Name>`, `child <Name>`, and `default`. Anything PathKit cannot trace back to one of those calls (a channel made with `workflow.NewChannel`, a future passed in as a parameter) is labelled as written: `receive ch`, `future f`, `send ch`.
- **Wait results are recognized only as a plain `ok` or `!ok`.** `if !ok` after `ok, err := workflow.AwaitWithTimeout(...)` has exits `signaled` / `timeout`; after `ReceiveWithTimeout`, or with `c.ReceiveAsync(&v)` inside the `if`, `received` / `not received`. A compound condition like `if ok && x > 0` is an ordinary `true` / `false` junction.
- **A `switch` with only a `default` is not a junction.** `fallthrough` into the next case is not a separate step: the path shows the case the switch chose.
- **A `switch` with no `default` always gets a `default` exit, even when that cannot happen** (for example when the cases cover every constant of a small status type). That path then shows as missed. Workaround: write the `default` yourself (for example one that returns an error), or mark the path with classification.
- **Case labels are the source text.** `case StatusApproved` prints the constant's name, not its value; `case "a", "b"` stays one exit. Two cases with the same text get ` #2`, ` #3`.
- **The saga note says a compensation `defer` is registered, not that it ran.** A `defer` counts as compensation when the deferred call starts an activity, local activity or child workflow, directly or inside a deferred `func`. Every path that gets past it shows `[compensation (defer)]`, including the successful path. "Compensation ran" and "did not run" are not separate paths, because counting them would create impossible paths (a successful order that also compensated). A `defer cancel()`, a deferred log line, a deferred call to your own helper, and a `defer` inside a selector callback get no note. The note is in the text output, not in the `--mermaid` diagram.

## Loops

- **Loops follow the loop rule.** A loop is a junction when it contains a Temporal call or any junction. It adds at most three kinds of path: not entered, entered and left from inside, and entered, went round, then left. A run that goes round many times is folded onto one of those by keeping only its last trip, so "failed on the 1st trip" and "failed on the 5th trip" are the same path, and the number of trips is never shown.
- **Any call into the Temporal SDK makes a loop a junction**, even one that does not wait, such as `workflow.GetLogger(ctx).Info(...)`.
- **A loop with no Temporal call and no junction is walked once.** PathKit assumes it runs its body once and records nothing for it. If such a loop's body can `return`, the paths where the loop is not entered are not listed; a `for {}` of this kind with no `break` has no normal way out, so its paths are not listed at all. PathKit warns about a workflow that ends up with no paths (in the text report and on stderr) and does not count it in the totals. A `for {}` loop that contains a Temporal call (a `workflow.Sleep`, say) but no `break` or `return` has no way out either, so it gets the same warning.
- **A `for {}` loop has no "not entered" path**: it always goes in, and leaves only by `break` or `return`.
- **A loop condition that is not of the plain type `bool` cannot be recorded**, for example `type Flag bool` and `for !done` with `var done Flag`, an alias of such a type, or a type parameter constrained by `~bool`. `pathkit test` and `pathkit prepare` stop before any test runs, with a message that names the condition and the fix: write `for bool(!done)`, or exclude the workflow in `.pathkitrc.json` with a reason. `analyze`, `coverage` and `report` are not affected, and neither are `if`, `switch`, `range` and `for {}` loops or a condition that compares (`for done != true`).

## Recording (`pathkit test`)

- **Coverage is recorded only by `pathkit test`, not by plain `go test`.** A plain `go test` compiles your original workflow files, so it records nothing while your tests still pass or fail as usual. `coverage` and `report` then say `no trace files found in <dir>; coverage is recorded only by "pathkit test" (plain "go test" records nothing)`. `pathkit prepare` prints the `-overlay` command for running `go test` yourself; it copies the code as it is at that moment, so after a change run `prepare` again (otherwise the traces are stale, and reported as such).
- **A skipped test records nothing, and PathKit does not tell you which tests were skipped.** The paths it would have run show as missed. Run `pathkit test ./... -- -v` to see the `SKIP` lines. A test that fails still records the paths its workflows took.
- **`pathkit test` always runs tests fresh.** It adds `-count=1` (unless you pass your own `-count`), because Go's cached test results would skip the tests and record nothing.
- **A trace does not say which test produced it.** The workflow runs on its own goroutine and cannot see the `TestXxx` that started it. To connect one test to its path, run just that test: `pathkit test <folder> -- -run '^TestName$'`.
- **A run counts only if it finished a `return` of the workflow function.** A run that panics (even while computing its return value), times out, or is stopped by the SDK is saved as `incomplete` and never matched. Trace files are written when the workflow function exits, so a run left blocked forever produces no trace.
- **The staleness hash ignores comments and formatting, but nothing else.** Renaming a variable inside the workflow function marks its old traces `stale`. Editing a different function, or another file, does not. The hash uses only the function's Go tokens, so it is the same on Linux, macOS and Windows.
- **Some names are reserved in recorded packages:** `pathkitRec`, `pathkitStart`, `pathkitRecorder`, `pathkitTrace`, `pathkitTraceDir`, `pathkitLoop`, `pathkitCtx` and `pathkitRet1`…`pathkitRet8`. If your package already uses one, recording stops with a clear error.
- **A workflow function with more than 8 results, or whose parameters have no names at all** (`func W(workflow.Context, int)`), cannot be recorded; `pathkit test` stops with a clear error. A context parameter written `_` is fine.
- **In a recorded `range` loop, PathKit adds a call after the loop's closing `}` and before each `break` that leaves it**, on the same lines, so line numbers do not change.
- **`pathkit test` writes its marked-up copies to `.pathkit/overlay/`** in the folder you run it from, and deletes only its own files there. Go's build and test commands never look there, but `gofmt -l .` does; add `.pathkit/` to your `.gitignore` and run gofmt on your tracked files.
- **Two workflows with the same package name and function name in different folders** are named with the shortest unique tail of their import path (`a/dup.Work`, `b/dup.Work`). With a `.pathkitrc.json` the names are decided over the config's packages; without one, over what the command loaded, so record and report on the same folder (`./...`). Trace files record the workflow's package; a trace that names another package is "unknown workflow", never counted.

- **Run `go test -overlay=...` from the real folder, not through a symbolic link.** A symbolic link is a folder name that points at another folder (macOS temporary folders are one: `/var` points at `/private/var`). `pathkit test` handles this itself. The command that `pathkit prepare` prints is run by your own shell, whose working folder keeps the link's name, and then the Go tool does not match the copied files and records no traces (`recorded 0 traces`). `cd` into the real folder (`cd -P .` does it) before running it.

## Coverage and reports

- **Branch coverage uses raw steps**, before loop folding, so a branch can show as taken even when no covered path uses it. It is shown only; `--fail-under` uses path coverage.
- **Traces that do not count never change the exit code.** A stale, unmatched, incomplete or unreadable trace is a warning on stderr and a number on the `Traces:` line. A CI job that must fail on those should check the `traces` counts in `--json`.
- **`--allow-stale` trusts that the change was cosmetic.** A stale trace that still fits a path is counted (marked `(stale trace)`), even if the change altered what that path does.
- **`coverage --clean` and `report --clean` delete traces only after a full report** (exit 0 or 2), never after an error.
- **Priority labels are per workflow, not per path.** High (below 50%), Medium (50–80%, both included) or Low (above 80%), compared exactly with whole numbers. A workflow with no paths gets no label.
- **Colour appears only on a real terminal**, never when the output is piped or redirected, with `--no-color`, config `noColor`, or `NO_COLOR`. The `--out` file and `--json` never have colour.
- **`report` takes folders, not single files.** With no folder it uses every entry of the config's `packages`; a workflow reached through two entries is counted once.
- **The HTML page is a snapshot of one run**, has no diagram (use `analyze --mermaid`), needs JavaScript for its path tables (the summary and the glossary work without it), and needs `=` to name a file (`--html=out.html`). Its trend covers the last 5 `report --html` runs written to that folder; a CI job starting from a fresh checkout starts the trend empty unless it keeps `report-history.json`.
- **`--version` shows a commit-based version for local builds**, for example `v0.0.0-20250101000000-abcdef123456+dirty`; `go run` prints `dev`. Only release builds and `go install ...@vX.Y.Z` show a clean `vX.Y.Z`.

## Scope (`.pathkitrc.json`)

- **`include` means "only these count".** Every other workflow is listed as excluded with the reason `not in include list`, never dropped silently.
- **An in-scope workflow PathKit cannot analyze is always printed, and blocks `coverage` and `report` with exit 1.** Fix it, or exclude it with a reason.
- **Names are checked against the whole configured `packages`**, so a misspelled name is caught even when you analyze one file; PathKit then loads those packages once more.
- **`pathkit test` and `pathkit traces` without a folder use the config's `packages` only when it lists exactly one.**
- **The config search stops at the folder with `go.mod`.** Use `--config <file>` to name a file anywhere. On Windows, a config path such as `/abs/x` (no drive letter) is relative to the config file; write `C:/abs/x`.

## Path classification

- **`stableId` changes when a condition's text changes.** It is built from the printed text of each decision, so renaming a variable in an `if` changes the `stableId` of every path through it, and a saved override or acceptance then shows as stale (a warning; the path is testable again). It does not change when an unrelated junction is added or removed. `pathkit explain` and `report --json` show the current ids.
- **A rule's entries are copied from `pathkit analyze`** and matched as exact text (spaces collapsed). A `when` entry that matches nothing makes the rule stale (a warning); a `without` entry that matches nothing is an error. A rule can only list decisions: it cannot say "this loop ran at least twice" or compare values.
- **Identical decision text must be numbered.** In a workflow with several decisions of the same text, write `if more #2 --false` (`#1` is the first) or `any: if more --false`. `#n` counts in source order, so a decision added above shifts it: `#2/3` turns the rule off with a warning when the count changes, and with a CI baseline every numbered entry warns when its decision changed place on the map. Without a baseline, a bare `#2` has no such protection. The place check can also warn when `#2` is still right, and cannot see two identical decisions whose bodies (with no decision inside) are swapped.
- **A `//pathkit:untestable` comment marks one exit of one decision**, on the decision's own line or the line above; a combination needs a rule. It is checked even when classification is off: one that cannot be used makes the workflow "not analyzable", never silently ignored.
- **Names in the classification section are checked against every top-level function**, so an override naming an unexported helper resolves and is then reported stale. Entries for excluded or unpicked workflows are neither applied nor checked.
- **The classification block is off unless asked for** (`--coverage-basis`, or `"classification": {"enabled": true}`). Off, `--fail-under` checks overall coverage exactly as without classification. The JSON has the classification fields all the time.
- **A trace that fits no path** makes that workflow's detector and rule claims needs-review until the trace is fixed, re-recorded or accepted in `classification.explained_traces` with a reason. Its steps id uses junction numbers, so it changes when the decisions are renumbered. A trace beyond the path cap is not counted as unexplained.
- **The CI baseline compares stable ids.** Editing a condition's text makes its paths look new, and a lost test is caught only while its path's stable id is unchanged. Paths beyond the path cap are not in the baseline.
- **`scripts/project-baseline.sh` builds a copy of the project.** A `replace ../sibling` in `go.mod` or a `go.work` pointing outside the project will not build in the copy.

## Automatic detectors

- **Not detected yet** (a person can still use the label with a mark or a rule): `dead-code` and `after-continue-as-new` (code after a `return` has no path), `update-handler-continue-as-new`, `rejected-update-invisible` and `unfinished-handlers` (handlers are not followed), `concurrency-order` (a person may set it), `workflow-task-failure` (paths into `panic` are dropped), `side-effect-error` (an error check after `SideEffect` is a junction only with `//pathkit:branch`), and `either-or-wait`. `model-limit` is set only by PathKit itself, on a claim it does not trust. `loop-minimum`, `set-then-test` and `depends-on-missing` are config rules only.
- **`closed-signal-channel` is an assessment, not a proof.** The Temporal SDK and server do not close signal channels, but code can turn another handle of the same named channel into a `workflow.Channel` with a type assertion and close it. So when the package has a type assertion on a channel interface, or passes a channel to another package, the claim is not made for the affected names and the path goes to needs-review. A channel declared with `var` and assigned later is "origin unknown" (needs-review).
- **What the automatic detectors assume about Temporal and your project.** These are things PathKit does not check, so a project that breaks one of them can have a path marked cannot-be-tested that a test could reach:
  - *SDK version:* "the SDK does not close signal channels" was checked in the source of one SDK version (v1.49.0, named in the `closed-signal-channel` definition). A much newer or older SDK was not read.
  - *No custom interceptors:* an interceptor is your own code, registered on the worker or on the test environment, that sits between the SDK and the workflow and can replace what a workflow call such as `workflow.GetSignalChannel` returns. One could hand the workflow a channel it has already closed. PathKit does not look for interceptors. If you use them, check the `closed-signal-channel` claims, or turn that detector off with a reason.
  - *Results are not changed after `Get`:* `contradictory-get-result` and `contradictory` assume that the value an activity result is decoded into is changed only by the workflow code PathKit reads. A test cannot change it afterwards: the result is decoded into a fresh value. A mock returns one result per call, and a retry happens before `Get` returns.
- **`contradictory`, `contradictory-get-result` and `same-list-loops` only claim what they can prove.** They use the compiler's single-assignment form and strict shape checks, so they miss many real cases and never guess. Not claimed: a decision inside a loop, a selector callback or a function literal; a value read through a pointer, from a map, from a channel or from a call; a list that is re-sliced, appended to or re-assigned; a `Get` in a loop, closure, `defer` or `go`.
- **`list-built-from-list` and `loop-exit-before-first-trip` claim only their exact shapes**: one plain append per trip into a list that starts empty and nothing else touches; a `for cond` loop on a local plain `bool` set to a constant. A flag set only by other conditions and tested later (a set-then-test shape) is not detected; use a rule.
- **`constant-condition` reads only `if` conditions** and never follows a constant from another package.
- **History limits and version gates can be tested.** The SDK's test environment has `SetContinueAsNewSuggested`, `SetCurrentHistoryLength`, `SetCurrentHistorySize` and `OnGetVersion`, so those paths are `needs-special-test`, not cannot-be-tested.
